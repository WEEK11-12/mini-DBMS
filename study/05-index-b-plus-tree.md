# 5. 인덱스와 B+ 트리

> - 선형 탐색 O(N)과 트리 탐색 O(log N)
> - B 트리와 B+ 트리의 차이, 노드 분할과 병합
> - 디스크 기반과 메모리 기반의 차이
> - WHERE id = ?에서 인덱스를 타는 경로와 못 타는 경로

---

## 선형 탐색 vs 트리 탐색
- **선형 탐색 $O(N)$** : 행을 앞에서부터 하나씩 확인. 찾는 행이 끝에 있거나 없다면 모든 행을 살펴보게 됨
- **트리 탐색 $O(\log N)$** : ID를 기준으로 정리된 인덱스에서 매 단계 찾을 범위를 좁혀감 
  <br> → 데이터가 많아져도 확인할 경로 짧게 유지 가능

---

## B+ 트리
#### B 트리 vs B+ 트리

| | B 트리 | B+ 트리|
| --- | --- | --- |
| 중간 노드 | 경계 키와 행 찾는 정보를 함께 가질 수 있음 | 경계 키로 길을 안내함 |
| 행 찾는 정보 | 중간 노드나 리프에 있음 | 리프에 모여 있음 |
|`id = 20` | 중간에서 찾기가 끝날 수 있음 | 리프까지 내려가서 찾음 |
- 행 찾는 정보 : 데이터를 이 위치에 그대로 저장하는 게 아니라 참조 등의 형태로 저장함


-  **B 트리** : 모든 노드가 행을 찾는 정보이자 실제 데이터
    ```plain text
    B 트리
                       [20→행 | 40→행]
                     /       |        \
             [5→행, 10→행] [30→행] [50→행, 60→행]
    ```
- **B+ 트리** : 실제 데이터는 리프에만 존재, 중간 노드는 어느 자식으로 내려갈지 알려주는 경계
  ```plain text
  B+ 트리
                         [20 | 40 | 60]
                      /     |     |    \
         [5→행, 10→행] [20→행, 30→행] [40→행, 50→행] [60→행]
  ```
  - **트리 높이가 낮아진다** :
    - 노드에 데이터까지 담게 되면 고정 크기의 노드 안에 담을 수 있는 정보의 '개수'가 줄어든다.
    - 노드에 경계 키만 담으면 담을 수 있는 키의 개수가 늘어나고, 자식으로 뻗어나가는 가지의 개수도 늘어난다 
  - **범위 조회에 유리하다** :
    - `id BETWEEN 20 AND 60`인 상황
    - B+ 트리 : 20이 있는 리프 찾은 뒤 순서대로 이어진 리프를 읽으면 됨
    - B 트리 : 리프만 고려하면 안 되기 때문에 복잡해짐

#### B+ 트리 노드 관리
- 노드 분할 : 새 항목을 노드에 추가하려 하는데 자리가 없을 때, 그 노드를 둘로 나누는 것.
  - 리프 하나가 넘칠 때 : 리프를 둘로 나누고, 부모의 경계 키도 추가
  - 부모 노드까지 꽉 찬 경우 : 부모도 분할해야 하고, 부모의 부모도 분할해야 함.
    - 최종적으로 맨 위까지 넘치면 트리가 한 단계 높아짐
- 노드 병합 : 삭제 후, 리프에 항목이 너무 적어지면 이웃 리프와 합침.

#### 디스크 vs 메모리
- 디스크 기반 : 노드가 메모리에 없다면 저장 위치에서 읽어와야 함.
  - 한 노드에 여러 경계 키를 담아서 **읽어야 할 노드 수를 줄이는 것이 중요함**.
- 메모리 기반 : 노드들이 메모리에 있으므로 저장 장치에서 노드를 읽어오는 과정 없이  따라갈 수 있음

## WHERE 조건과 인덱스
#### 인덱스를 타는 경로
``` sql
SELECT * FROM users WHERE id = 50;
```
- ID를 B+ 트리에 등록하므로, B+ 트리에서 50을 찾고 연결된 행을 읽는 경로 사용 가능
#### 인덱스를 못 타는 경로
``` sql
SELECT * FROM users WHERE email = 'a@example.com';
```
- 인덱스를 만들지 않은 열을 조건으로 사용하면, **선형 탐색**이 필요함.
