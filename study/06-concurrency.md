# 6. 동시성과 서버 구조

> - 스레드 풀 개념과 요청 처리 흐름
> - 경쟁 상태(race condition), 뮤텍스, 읽기/쓰기 락
> - 엔진과 API 서버 사이의 인터페이스 설계

---

## 스레드 풀
- **스레드 풀** : 미리 준비한 작업자 스레드들이 들어온 요청을 나눠서 처리.
- 고정된 스레드 개수 → 여러 요청을 동시에 다루면서도 한꺼번에 실행되는 작업 수를 제한 가능
  - `핵심 1` : 스레드를 재사용
  - `핵심 2` : 요청이 몰릴 때 서버 자원이 무제한으로 쓰이지 않도록 조절 (동시 실행 작업 수 제한)
- 스레드 풀은 병렬 처리를 가능하게 해도, _공유 데이터의 안전까지 보장하지는 않음_ (추가 도구 필요)

---

## 경쟁 상태 (race condition)
- **경쟁 상태** : 여러 스레드가 같은 데이터를 다룰 때, 실행 순서에 따라 결과가 달라지는 문제
- 예시
  ``` plain text
  스레드 A: 다음 ID 8을 읽음
  스레드 B: 다음 ID 8을 읽음
  스레드 A: 새 행에 ID 8을 부여
  스레드 B: 새 행에 ID 8을 부여
  ```
  - `읽기 → ID 부여 → 다음 값 변경`을 여러 스레드가 안전하게 나눠 처리하지 못함 
- **뮤텍스**, **읽기/쓰기 락** 등의 도구로 해결 가능

#### 뮤텍스 (mutex)
- **뮤텍스** : 한 번에 한 스레드만 정해진 작업 구간에 들어가게 함
- 전제 : 일련의 작업 구간을 보호 구간으로 묶음 (예 : `읽기 → ID 부여 → 다음 값 변경`)
- 동작 : 한 스레드가 작업 구간을 실행하는 동안, 그 구간을 실행하고자 하는 다른 스레드는 기다림.
  - 스레드의 동작 전체를 무조건 막는 것이 아니라, **겹치면 안 되는 공유 데이터 작업**을 보호하는 것

#### 읽기/쓰기 락
- **읽기/쓰기 락** : 읽기끼리는 함께 허용, 쓰기가 포함되면 충돌을 막는 방식
  - 읽기 쓰기 락도 뮤텍스처럼 겹치면 안 되는 공유 데이터 작업을 보호하는 목적으로 사용됨.
  - 두 요청이 같은 데이터를 `SELECT` → 둘 다 값을 바꾸지 않으므로 **함께 읽기 가능**
  - 둘 중 한 요청이`INSERT`로 데이터 변경 → 데이터 변경 중의 읽기 혹은 쓰기가 문제 초래할 수 있으므로 **조율**
- 뮤텍스와 다르게 항상 동시 접근을 금지하는 게 아니라, 서로 충돌하는 접근인지 구분한다는 점이 특징.

## 엔진 ↔ API 서버 인터페이스
- "요청을 받는 일" vs "SQL을 처리하는 일" 구분 필요
  ``` plain text
    클라이언트    →    API 서버    →    DB 엔진    →    API 서버    →    클라이언트
                   (요청 전달)   (SQL 처리·결과 반환)   (응답 전달)

  ```
- **API 서버** : 외부 요청을 받아 내부 엔진에 전달, 엔진의 응답 결과를 다시 전달
- **엔진** : SQL 처리기와 인덱스를 이용해 결과를 반환
- **인터페이스** : API 서버와 엔진 사이에 '무엇을 전달할지', '어떤 결과를 돌려받을지' 정한 약속
- 과제 상황 :
  - Phase 03에서 Phase 01의 SQL 처리기와 Phase 02의 B+ 트리 인덱스를 내부 엔진으로 재사용
  - 기존 로직에 API 서버로 감싸는 작업만 추가하면 됨
  - 인터페이스 기반으로 설계하면, 요청을 받는 방식이 바뀌어도 SQL 처리의 핵심 역할을 구별할 수 있다.
