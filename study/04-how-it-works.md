# 4. DBMS 내부 구조 (과제와 직결)

> - 전체 처리 흐름: 클라이언트 → 파서 → 옵티마이저 → 실행 엔진 → 저장 엔진
> - SQL 파싱: 토큰화, 구문 분석, 구조화된 결과(AST)
> - 저장 방식: 레코드와 페이지, 힙 파일, CSV/바이너리 포맷 설계의 트레이드오프

--- 

## DBMS 내부 데이터 처리
> **클라이언트** → **파서** → **옵티마이저** → **실행 엔진** → **저장 엔진**
- **역할 분리** : 무엇을 요청했는지 이해하는 일 ↔ 데이터를 어떻게 찾을지 결정하는 일
- `파서` : 문장 해석 
- `옵티마이저` : 데이터를 찾을 경로 선택
- `실행 엔진` : 경로를 따라 조회 수행
- `저장 엔진` : 실제 저장된 데이터에 접근

#### SQL 파싱
- **토큰화** : SQL 문장을 의미 있는 조각으로 나누는 일
  ``` sql
  SELECT * FROM users WHERE id = 7
  ```
  결과 : `SELECT`/`*`/`FROM`/`users`/`WHERE`/`id`/`=`/`7`
- AST : 토큰을 나눈 후, 그 조각들이 이루는 구조
  ``` plain text
  조회문
  ├─ 대상 테이블: users
  ├─ 가져올 열: *
  └─ 조건: id = 7
  ```
- **필요성** :
  - 토큰화만으로는 문장의 뜻을 이해할 수 없음 → **각 조각 간의 관계를 읽어서 구조화**
  - 실행 엔진이 원래 문장을 다시 읽으며 WHERE을 찾는 대신, 파서가 정리한 대상 테이블, 열, 조건을 받아 동작할 수 있음

---

## 데이터 저장 방식
- **레코드** : 한 행의 데이터
- **페이지** : 저장소가 데이터를 일정한 크기로 묶어 다루는 단위 (레코드 여러 개를 담는 DBMS의 저장단위)
  - 저장소에서 행을 매번 따로 읽고 쓰기보다, 일정한 단위로 관리하기 위해 구분함. (캐시 히트 등의 이점)
  - 과제 요구사항에서 페이지 구현은 빠져 있음

#### 힙 파일
- **힙 파일** : 레코드를 특정 열의 순서대로 정렬해두지 않고 저장하는 방식
  - 자료구조의 힙 정렬과 무관함
  - ID 순서 유지가 안 되기 때문에, 행을 찾으려면 여러 레코드를 살펴야 한다 → **인덱스의 중요성 증가**

#### 데이터 저장 포맷
- 옵션 : CSV, 바이너리, 자체 형식
- **CSV** :
  - 장 : 사람이 파일을 열어 내용을 확인하기 쉬움.
  - 단 : 값 자체에 쉼표나 줄바꿈이 들어가면 어디까지가 한 값인지 구분하는 규칙이 필요.
- **바이너리** :
  - 장 : 정해진 구조에 맞춰 값을 저장하므로 프로그램이 읽을 위치를 다루기 좋음
  - 단 : 사람이 이해하기 어려움
- 트레이드오프 : 읽기 쉬움 ↔ 저장 방식 ↔ 해석 방식
