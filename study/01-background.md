# 1. DBMS는 왜 등장했나 (역사와 배경)

> - 파일 시스템으로 데이터를 관리할 때 생기는 문제: 중복, 불일치, 동시 접근, 장애 복구, 보안
> - 계층형 DB와 네트워크형 DB에서 관계형 DB로의 흐름 (Codd의 관계형 모델, SQL의 탄생)
> - 이후의 흐름: RDBMS 전성기, NoSQL(Redis 등)의 등장, 지금의 공존

---

## 필요성
- **핵심 질문** : 여러 프로그램과 사람이 같은 데이터를 밑고 사용할 수 있는가?
- **관련 문제** : `orders.csv`와 `shipping.csv`에 각각 고객의 정보를 적어둔다면?
  - 데이터 중복 : 고객의 주소를 수정한다면? (두 파일을 모두 수정해야 함 → 불일치 가능성 높아짐)
  - 동시 접근 : 두 요청이 동시에 같은 고객 정보를 바꾼다면?
  - 장애 후 복구 : 저장 도중 프로그램이 꺼진다면?
  - 접근 권한
- **DBMS의 필요성** : 데이터를 저장하는 데 그치지 않고, 위와 같은 공통 문제를 한곳에서 다루기 위해 등장.

#### 데이터 중복
- 여러 복사본 사이의 일관성 문제
- 파일을 사용한다 != DBMS
- 데이터 중복 문제는 파일 저장 자체의 한계가 아니라, 중복된 데이터를 일관되게 관리할 장치가 없는 문제
- 핵심 : 파일 위에서 어떤 규칙과 기능을 제공하는가?
#### 동시 접근
- 같은 데이터에 동시에 접근할 때의 일관성 문제
- 데이터가 하나의 파일에 기록되어 중복이 없더라도, 문제는 발생할 수 있음
- 예시 : 재고가 1 개인 상황에서 두 구매 요청이 거의 동시에 재고 확인 → 한 개뿐인 물건을 두 번 판매
- 관련 개념 : _트랜잭션_ (경계 : 파일을 읽는 순간이 아니라, 읽은 값을 근거로 변경을 확정할 때까지)
#### 장애 후 복구
- 작업이 중간에 끊길 때의 문제
- 작업 도중 프로그램이나 컴퓨터가 멈춰도, 데이터가 어느 상태로 남아야 하는지 정할 수 있어야 함
- 예시 : 계좌 A에서 계좌 B로 송금하는 상황에서, A의 잔액을 줄여 파일에 저장한 직후 프로그램이 꺼진다면?
- 트랜잭션이 여기서도 중요함. (둘 다 반영된 상태이거나, 둘 다 반영되지 않은 상태)
#### 보안과 접근 권한
- 누가 어떤 데이터에 어떤 작업을 할 수 있는가?
- DBMS는 데이터에 접근하는 공통 창구가 되어, 사용자나 역할에 따라 권한을 나눌 수 있음
- 예시 : MySQL에서 특정 계정에 `SELECT`는 허용하고, `INSERT`는 허용하지 않음
- 핵심 : 보안은 데이터를 숨기는 것만이 아니라, 필요한 접근만 허용하는 것

## 관계형 DB

#### DB 구조의 변화
- **관점** : 데이터를 어떻게 연결하고 찾아갈 것인가?
- 기존의 구조 비교 (경로 중심)
  - **계층형** : 부모-자식 관계를 따라 내려가는 구조 (예 : 회사 → 부서 → 직원)
  - **네트워크형** : 한 데이터가 여러 데이터와 연결될 수 있음(유연), 하지만 연결 경로를 의식해서 찾아가야 함.
- **관계형** :
  - 어느 연결을 따라갈까? < **어떤 데이터가 필요한가?**
  - 데이터를 "관계"로 표현 → 원하는 결과와 연결 조건으로 데이터를 찾음 (`JOIN`)
  - 테이블 자체를 찾기 위한 "경로"가 여전히 필요하지만, 경로를 정하는 책임이 사용자 프로그램이 아닌 DBMS에게 있음.
#### SQL
> **관계형 모델** : 데이터를 바라보는 방식. <br>
> **SQL** : 그 데이터에 질의하는 언어.
- SQL의 중요성 : 사용자가 데이터에 도달하는 _절차_보다 원하는 "**결과**"를 표현할 수 있게 해줬기 때문
  ```sql
  SELECT e.name, d.name
  FROM employees AS e
  JOIN departments AS d ON e.department_id = d.id
  WHERE e.id = 7;
  ```
  - 위 쿼리는 단순히 "직원 7의 이름과 그 직원이 속한 부서의 이름을 달라"고 함. (`결과`)
  - 어느 테이블을 먼저 읽을 건지, 몇 건을 볼 건지, 인덱스를 사용할지 등을 지정하지 않음. (`절차`)
#### 관계형 DBMS의 발전 배경
- **요구사항** :
  - 데이터를 믿고 관리하기 위한 기능 제공 (DBMS)
  - 다양한 질문에 맞춰 조회할 수 있는 시스템 (SQL & RDB)
- **RDB의 요구사항 충족** :
  - 정해진 탐색 경로 하나에만 묶이지 않음 → 데이터에 대한 새로운 질문을 SQL로 표현하기 좋음
  - 모든 데이터와 사용 방식에 관계형 DBMS가 가장 알맞다는 것은 아님. (NoSQL)
- **NoSQL의 등장** :
  - 데이터와 사용 방식에 따라 다른 선택지도 필요해짐 (RDBMS의 실패가 아님)
    - 자주 읽는 데이터나, 짧게 유지할 상태 등을 위한 시스템 필요 → Redis 같은 NoSQL 등장
  - NoSQL은 관계형 테이블 중심이 아닌 여러 데이터베이스를 묶어 부르는 넓은 단어임
    - 각각 다루는 데이터 형태와 잘하는 일이 다름
    - "RDBMS는 느리고, NoSQL은 빠르다"처럼 나누면 핵심을 놓침.
    - 무엇을 저장하고 어떤 질문을 자주 하는지가 선택의 기준이 됨.
