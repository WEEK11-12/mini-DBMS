# 2. 언제, 왜 DBMS를 쓰나
> - 파일 저장, 엑셀, DBMS 비교
> - RDBMS와 NoSQL의 선택 기준
> - 서비스 구조에서 DBMS가 놓이는 자리(앱 서버 ↔ DB)

--- 

## 데이터 저장 도구 비교
- **파일** : 프로그램이 읽고 쓰기 좋지만, 데이터 관리 규칙은 프로그램이 직접 마련해야 함
- **엑셀** : 사람이 읽고 관리하기 편함. 하지만 여러 요청이 동시에 접근할 때, 충돌을 다루기 어려움
- **DBMS** : 데이터 저장 + 공통된 규칙을 정의하고 있기 때문에 처음부터 만들 필요 없음
  - DBMS가 모든 문제를 자동으로 해결해주지는 않음.
  - 다만, 제약 조건, 트랜잭션, 권한 같은 수단을 제공하고, 사용하는 쪽에서 어떤 규칙을 적용할지 정해야 함.
  - DBMS가 업무 규칙을 스스로 알 수 없기 때문 
    <br>(예 : 중복되면 안 되는 데이터는?, 동시에 접근해도 상관 없는 데이터는?)
  - **업무마다 다른 규칙은 사용자가 지정, DBMS는 지정된 규칙을 지키는 역할**

--- 

## RDBMS와 NoSQL의 선택 기준
- 어느 쪽이 더 빠른가 ? (X)
- 데이터 사이의 관계와 지켜야 할 규칙이 무엇인가 ? (0)

#### RDBMS가 적합한 상황
- `관계` : 특정 데이터가 반드시 다른 데이터와 연결되어야 하는 상황 (예 : 주문 - 회원)
- `트랜잭션` : 데이터의 연쇄적인 처리가 한 작업으로 이루어져야 할 경우 (예 : 주문 → 재고 변경)
- `제약` : 특정 데이터의 고유성(중복 금지)이 보장되어야 하는 등의 상황 (예 : 회원 이메일)

#### NoSQL이 적합한 상황
- 값을 빠르게 찾고, 일정 시간이 지나면 없애는 등의 상황 (예 : 로그인 세션)
- DB의 유연한 문서 구조가 필요한 경우 (예 : 상품마다 속성이 크게 다를 때)

---

## 앱 서버 ↔ DB
> **흐름** : 사용자 → 앱 서버 → DBMS → 앱 서버 → 사용자

#### 앱 서버 
- 역할 : 누가 요청했는지 확인하고, 어떤 데이터를 요청할지 결정
- 사용자가 보통 DBMS에 직접 요청하지 않음.
- 서비스 규칙을 앱 서버가 판단 → DBMS에게 요청

#### DBMS
- 역할 : 앱 서버가 보낸 조회 요청에 따라 저장된 데이터를 찾고 반환
- 저장, 조회와 자신에게 설정된 제약, 권한에 따라 요청을 처리

#### 과제 상황
- 데이터 처리 요청이 들어오는 입구가 Phase마다 달라짐.
- **Phase 01** : CLI → DB 엔진부터 바로 시작
