# API 서버와 내부 엔진 연결

> 전체가 예습 정리입니다. 프로그래밍 언어·프레임워크·API 계약은 아직 선택하지 않았습니다.

## CLI와 API는 같은 엔진을 호출한다

```text
CLI → SQL 문자열 ┐
                 ├→ 파싱·검증·실행 → 파일 + B+ 트리
API → SQL 문자열 ┘
```

API 서버에서 SQL 파서나 저장 로직을 다시 만들지 않습니다. 입력을 받고 엔진을 호출한 뒤 결과를 응답하는 역할을 담당합니다. 재사용할 엔진은 결과를 반환하고, 터미널 출력은 CLI가 맡는 구성이 가능합니다.

## 요청 하나의 흐름

```text
클라이언트 요청
→ 요청 형식·크기 검사
→ 스레드 풀에 작업 제출
→ 공통 엔진으로 SQL 실행
→ 성공 결과 또는 오류를 구조화
→ 요청한 클라이언트에 응답
```

HTTP와 JSON을 사용한다면 SQL 문자열을 받은 뒤 컬럼·행·영향받은 행 수 등을 JSON으로 반환하는 계약을 정할 수 있습니다. 이는 예시이며 과제는 특정 프로토콜을 지정하지 않았습니다.

요청 하나당 SQL 한 문장으로 제한하면 초기 구현의 오류 경계가 단순해집니다. 여러 문장을 허용할지는 별도 선택입니다. CLI의 “SQL 파일에서 첫 오류 후 중단”과 “어떤 클라이언트의 오류 때문에 서버 전체를 중단”은 다릅니다. 일반적인 입력 오류는 그 요청만 실패시킵니다.

## 서버 경계에서 확인할 것

입력 SQL이 문자열인지, 빈 값인지, 너무 크지 않은지 확인합니다. 테이블 이름을 파일 경로에 그대로 연결하면 경로 이탈이 가능하므로, 사전 정의한 스키마에서 테이블과 실제 파일을 매핑해야 합니다.

의도적으로 SQL을 받는 API이므로 임의 SQL 실행 범위를 제한해야 합니다. 지원하지 않는 구문은 거부합니다. 외부에 공개한다면 인증·접근 범위가 별도로 필요하며, 네트워크로 접근할 수 있다는 것과 인터넷에 무인증 공개한다는 것은 다릅니다.

내부 파일 경로·스택 추적 같은 상세 오류는 클라이언트 응답에 그대로 노출하지 않습니다. 정상 SQL 오류, 용량 초과, 엔진 장애를 구분해 응답 정책을 정합니다.

## 시작과 종료

서버가 요청을 받기 전에 스키마·파일을 검사하고 인덱스를 재구성합니다. 종료 시 새 요청을 막고 이미 진행 중인 작업을 어떻게 마무리할지 정한 뒤 파일 자원을 닫습니다.

파일 기록·인덱스 상태가 불확실해졌다면 일반 입력 오류처럼 넘기지 않고 엔진의 추가 작업을 제한해야 합니다.
