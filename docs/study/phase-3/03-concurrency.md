# 동시성과 데이터 일관성

> 전체가 예습 정리입니다. 아래 단순 잠금은 초기 설계 후보이며 확정 구현이 아닙니다.

## 두 요청이 같은 상태를 읽으면 생기는 문제

다음 ID가 42일 때 요청 A와 B가 동시에 읽으면 둘 다 42를 부여할 수 있습니다. 카운터를 읽고 증가시키는 전체 동작이 보호되어야 합니다.

파일만 잠가도 충분하지 않을 수 있습니다. A가 파일에 행을 쓰고 인덱스에 넣기 전에 B가 조회하면, 스캔으로는 보이고 인덱스로는 안 보이는 순간이 생길 수 있습니다.

B+ 트리 분할은 여러 키·자식·리프 연결을 바꾸므로 중간 상태를 다른 스레드가 읽는 것도 위험합니다.

## 보호할 것은 하나의 논리적 변경이다

```text
잠금 획득
→ ID 부여
→ 파일 기록
→ 인덱스 등록
→ 관련 공유 상태 확정
잠금 해제
```

각 줄에 따로 잠금을 거는 것과 전체 변경을 보호하는 것은 다릅니다. 조회도 같은 동기화 규칙에 참여해야 중간 상태를 보지 않습니다.

검증·파싱처럼 공유 데이터와 무관한 작업은 임계 구역 밖에서 처리할 수 있지만, 검증이 읽는 스키마가 변경 가능한지 등 전제도 확인해야 합니다.

## 처음에는 굵은 잠금으로 정확성을 확인할 수 있다

하나의 엔진 뮤텍스로 DB 접근 전체를 보호하면 구조가 단순합니다. 대신 DB 실행 구간이 직렬화되므로 여러 워커가 있어도 엔진 처리량이 늘지 않을 수 있습니다.

다음 단계로 읽기/쓰기 락을 쓰면 여러 읽기를 함께 허용하고 쓰기는 독점할 수 있습니다. 그러나 공유 파일 핸들의 seek 위치도 상태이므로, 읽기끼리 안전하려면 독립 핸들이나 위치 지정 읽기 등도 고려해야 합니다. 파일 seek 후 read를 무보호로 공유하면 다른 행을 읽을 수 있습니다.

테이블별·노드별 잠금은 병렬성을 늘릴 수 있지만 잠금 순서·분할·복구가 복잡해집니다. 먼저 정확성 증거를 만들고 실제 병목이 있을 때 좁힙니다.

## 락이 해결하지 않는 문제

락은 살아 있는 실행들 사이의 순서를 조정합니다. 정전·프로세스 종료 시 파일을 복구하거나 여러 SQL을 함께 취소하는 기능은 아닙니다.

단일 프로세스의 뮤텍스는 다른 프로세스나 CLI가 같은 파일을 직접 수정하는 것을 막지 못합니다. 서버 실행 중에는 파일 소유자를 하나로 제한하거나 프로세스 사이의 잠금 정책이 필요합니다.

SQLite도 스레딩 모드와 연결 사용 규칙을 구분합니다. 라이브러리를 쓴다고 모든 공유 방식이 안전한 것은 아닙니다. [SQLite 스레딩 모드](https://www.sqlite.org/threadsafe.html)

## 교착과 예외

여러 락을 쓸 때 A는 파일 락 뒤 트리 락, B는 트리 락 뒤 파일 락을 잡으면 서로 기다릴 수 있습니다. 잠금 순서를 통일하고 예외 때도 해제되게 합니다.

파일 기록 후 인덱스 등록이 실패했다면 추가 요청을 계속 받지 않고, 일관성 복구·재구성 정책으로 넘겨야 합니다. 단순 뮤텍스만으로 실패 원자성이 생기지는 않습니다.

## 확인할 증거

동시 INSERT 후 ID 중복·누락·행 수를 검사합니다. 쓰기와 조회를 겹쳐 파일·인덱스 결과를 비교합니다. 최종 행 수만 같다고 모든 중간 상태가 안전했던 것은 아니므로, 분할·ID 부여·파일 기록 사이에 실행을 겹치도록 제어한 테스트도 필요합니다.
