# 스레드 풀과 요청 처리

> 전체가 예습 정리입니다. 사용 라이브러리와 풀 크기는 미정입니다.

## 요청마다 새 스레드를 무제한 만들지 않는다

스레드 풀은 정해진 수의 작업 스레드를 재사용합니다. 도착한 요청을 작업으로 등록하면 여유 있는 스레드가 처리합니다.

```text
요청 A ─┐               ┌→ 워커 1 → 엔진 → A 응답
요청 B ─┼→ 작업 대기열 ─┼→ 워커 2 → 엔진 → B 응답
요청 C ─┘               └→ 여유 워커가 생기면 처리
```

스레드 하나가 요청 하나를 처리하는 동안 다른 스레드가 다른 요청을 처리할 수 있습니다. 내부 저장 작업이 같은 잠금을 요구하면 그 구간은 차례로 실행됩니다.

## 작업과 결과를 연결한다

작업 제출 결과를 Future 같은 객체로 추적하면 성공 값이나 예외를 원래 요청에 전달할 수 있습니다. 응답을 만들기 전에 파일·인덱스 변경이 끝났는지 확인해야 합니다.

Python의 ThreadPoolExecutor는 이런 풀과 Future의 한 예입니다. 공식 문서에는 동일 풀의 작업이 다른 Future 결과를 기다리다가 교착될 수 있는 사례도 있습니다. 언어를 Python으로 선택했다는 뜻은 아닙니다. [Python concurrent.futures](https://docs.python.org/3.14/library/concurrent.futures.html)

## 스레드 수와 대기열은 별개다

작업 스레드를 4개로 제한해도 대기 작업이 무제한 쌓이면 메모리와 지연이 계속 늘어날 수 있습니다. 큐 한도·진입 제한과 과부하 응답을 설계해야 합니다. 선택한 실행기가 큐를 자동으로 제한하는지 확인합니다.

풀 크기는 실제 저장장치·잠금 경쟁·작업 종류를 보고 정합니다. 크게 만들면 무조건 빨라지는 것이 아닙니다.

## 타임아웃이 작업 취소를 뜻하지 않는다

클라이언트가 기다리기를 포기해도 이미 실행 중인 INSERT는 계속될 수 있습니다. 타임아웃 후 같은 요청을 재전송하면 중복 삽입 위험이 있습니다.

요청 취소 가능 범위와 재시도 정책을 정해야 합니다. 중복 방지 키는 확장 후보이며, 구현하지 않았다면 자동 재시도가 안전하다고 약속하지 않습니다.

## 병렬 처리의 한계

I/O 대기와 CPU 실행은 다릅니다. Python의 일반적인 GIL 구성에서는 스레드 수만으로 CPU 중심 파싱·트리 계산의 다중 코어 실행을 보장하지 않습니다. 다른 언어나 런타임은 실행 조건이 다릅니다.

과제의 스레드 풀 요청 처리와 성능 향상 주장은 따로 검증합니다. 모든 요청이 사실상 하나씩만 실행되는지, 실제로 작업이 겹치는지도 관찰합니다.

## 종료와 실패

새 작업 접수를 멈춘 뒤 대기·실행 작업의 처리 정책을 적용합니다. 예외가 나도 Future를 회수하고 결과를 응답해야 합니다. 락과 파일 핸들은 실패 경로에서도 정리합니다.
