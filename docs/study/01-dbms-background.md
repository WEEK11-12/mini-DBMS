# DBMS 등장 배경과 파일시스템 비교

> 기존 질의응답만으로 확인하지 못한 배경을 이번 요청에 따라 보충한 노트입니다. 아래 업무 사례는 문제를 이해하기 위한 예시이며 특정 제품의 역사적 사건을 재현한 것이 아닙니다.

## 처음에는 프로그램이 자기 파일을 관리하면 됐다

직원 급여를 계산하는 프로그램 하나를 생각해 봅니다. 직원 번호, 이름, 급여를 파일에 기록하고, 필요할 때 읽어서 계산하면 됩니다. 프로그램을 만드는 사람이 파일 형식을 정하고 읽기·쓰기 코드를 작성하면 업무를 처리할 수 있습니다.

문제는 파일에 저장할 수 없다는 것이 아니라, 업무와 프로그램이 늘어날 때 생깁니다. 인사·급여·영업 프로그램이 같은 직원이나 고객 정보를 필요로 하면 데이터를 어느 파일에 두고, 누가 수정하며, 다른 프로그램이 어떻게 읽을지 함께 정해야 합니다.

## 데이터를 공유하면서 어떤 일이 생겼는가

### 같은 사실을 여러 파일에 복사한다

급여 프로그램과 인사 프로그램이 각각 직원 주소를 보관한다고 가정합니다. 주소가 바뀌었을 때 인사 파일만 고치면 두 파일은 서로 다른 주소를 갖습니다.

파일 읽기·쓰기는 모두 성공했어도 업무 데이터는 불일치합니다. 프로그램마다 별도로 복사하고 갱신하는 방식에서는 무엇이 현재 값인지, 어떤 복사본까지 수정해야 하는지를 계속 관리해야 합니다.

### 저장 형식이 바뀌면 여러 프로그램을 고친다

프로그램들이 직원 파일의 세 번째 항목을 급여로 읽고 있었는데, 중간에 새 항목을 넣으면 읽기 코드가 잘못된 값을 사용할 수 있습니다. 파일을 나누거나 검색용 구조를 바꾸는 일도 그 파일 구조를 아는 프로그램에 영향을 줍니다.

저장 구조에 대한 지식이 여러 프로그램에 퍼질수록 변경할 곳과 서로 맞춰야 할 규칙이 늘어납니다. 데이터가 어디에 어떻게 배치되는지와, 업무에서 어떤 데이터를 요청하는지를 분리할 필요가 생깁니다.

### 새로운 조회마다 읽기 코드를 만든다

처음에는 직원 번호로만 조회하던 업무가 나중에는 부서별 급여 합계나 특정 조건의 직원 목록을 요구할 수 있습니다. 파일에서 조건을 검사하고 집계하는 코드를 업무마다 작성하면, 데이터 접근 로직도 반복됩니다.

### 여러 작업과 실패를 함께 다뤄야 한다

두 프로그램이 같은 잔액 100을 읽고 각자 계산한 값을 덮어쓰면 한쪽 변경을 잃을 수 있습니다. 두 계좌 사이의 송금에서 한 파일만 바꾼 뒤 프로그램이 종료되면 두 변경 중 일부만 남을 수도 있습니다.

이 사례들은 동시성과 복구가 왜 필요해지는지를 보여줍니다. 구체적인 잠금·트랜잭션·복구 알고리즘은 아직 학습하지 않았습니다.

## 그래서 공통으로 데이터를 관리하는 소프트웨어가 필요해졌다

각 프로그램이 데이터 형식, 검색, 갱신, 공유 규칙을 따로 맡는 대신, 여러 프로그램이 사용하는 데이터를 관리하는 공통 계층을 두게 됩니다. DBMS는 데이터의 구조와 접근·변경을 관리하는 소프트웨어입니다.

어떤 기능이 필요해지는지는 앞의 상황과 연결해서 이해할 수 있습니다.

| 발생한 상황 | 공통으로 관리할 필요가 생긴 것 |
| --- | --- |
| 같은 사실을 여러 프로그램에서 사용 | 공유할 데이터와 중복·변경 규칙 |
| 파일 배치나 형식 변경이 업무 코드로 전파 | 논리적인 데이터 구조와 실제 저장 방식 사이의 경계 |
| 업무마다 다른 조건의 검색이 필요 | 공통 데이터 접근·질의 기능 |
| 동시에 읽고 수정하거나 중간에 실패 | 변경 순서와 실패 후 상태를 관리하는 기능 |

이는 DBMS 한 제품이 모든 문제를 한 번에 해결하며 탄생했다는 설명은 아닙니다. 데이터 관리 시스템과 기능은 서로 다른 요구에 대응하며 발전했습니다.

## DBMS와 관계형 DBMS의 등장은 구분한다

SQL이나 테이블 모델이 등장하기 전에도 계층형·네트워크형 데이터베이스가 있었습니다. DBMS의 등장을 곧 SQL의 등장으로 이해하면 안 됩니다.

IBM의 역사 자료는 1960년대 대량 데이터 관리에서 복잡한 계층·탐색 구조를 알아야 정보를 찾을 수 있었고, 조회를 위해 별도 프로그램을 작성해야 했다고 설명합니다. Codd는 1970년 관계형 모델을 제시하며 사용자가 물리적 저장 구조를 몰라도 데이터를 다룰 수 있는 방향을 제안했습니다. 이 부분은 관계형 모델이 나온 배경입니다. [IBM — The relational database](https://www.ibm.com/history/relational-database)

즉, 공유 데이터를 관리할 필요가 DBMS의 배경이고, 저장 구조와 접근 경로에 대한 의존을 줄이려는 요구는 관계형 모델의 배경을 이해하는 데 중요합니다.

## 파일시스템과 무엇이 다른가

파일시스템은 이름과 경로로 파일을 관리하고, 파일의 바이트를 읽고 쓰는 기반입니다. 일반적으로 파일 속의 `age`가 정수인지, 직원 번호가 중복되는지, 두 계좌 변경이 한 업무인지까지는 해석하지 않습니다. 그런 의미는 애플리케이션이나 DBMS가 담당합니다.

| 관점 | 파일시스템을 직접 사용하는 프로그램 | DBMS를 사용하는 프로그램 |
| --- | --- | --- |
| 저장 단위로 다루는 것 | 파일·바이트를 읽고 프로그램이 의미를 해석 | 레코드·컬럼 등 DBMS의 데이터 모델로 요청 |
| 형식·자료형 검사 | 프로그램이 읽기·검사 규칙을 구현 | 지원하는 스키마·제약 기능으로 공통 관리 |
| 조건 조회 | 프로그램이 탐색·필터 코드를 구현 | 지원하는 질의 인터페이스로 요청 |
| 여러 변경의 관계 | 프로그램이 직접 조정해야 함 | 지원하는 트랜잭션 기능 등을 활용 |
| 동시 접근 | 파일 잠금 등 기반 기능을 조합해 조정 | DBMS의 동시성 정책에 따라 조정 |

파일시스템에도 잠금·권한·복구를 위한 기능이 있을 수 있습니다. 그것만으로 업무 데이터의 의미와 여러 변경 사이의 관계까지 자동으로 보장되는 것은 아니라는 구분입니다. 반대로 모든 DBMS가 동일한 기능이나 보장을 제공하는 것도 아닙니다.

DBMS도 보통 파일시스템 위의 파일을 사용합니다. 예를 들어 PostgreSQL 공식 문서는 서버 프로세스가 데이터베이스 파일을 관리하고 클라이언트의 데이터베이스 작업을 수행한다고 설명합니다. [PostgreSQL — Architectural Fundamentals](https://www.postgresql.org/docs/18/tutorial-arch.html)

```text
업무 프로그램이 직접 파일 사용:
업무 프로그램 → 직접 작성한 데이터 처리 코드 → 파일시스템 → 저장장치

DBMS를 사용:
업무 프로그램 → DBMS의 데이터 처리 기능 → 파일시스템 → 저장장치
```

위 그림은 일반적인 파일 기반 구성을 단순화한 것입니다. 이번 과제도 파일을 없애는 작업이 아니라, 파일에 저장한 데이터를 INSERT / SELECT로 다룰 수 있도록 처리 계층을 만드는 작업으로 볼 수 있습니다.

## 이번 과제와 연결

Phase 1에서 파서, 스키마 검사, 실행기, 파일 읽기·쓰기 역할을 나누어 이해하는 이유도 여기 있습니다. SQL 요청을 실제 저장 바이트로 연결하되, 각 요청을 처리할 때 파일 형식의 모든 규칙을 새로 작성하지 않도록 공통 처리기를 만듭니다.

실제 저장 형식과 모듈 구조는 아직 결정하지 않았습니다. 앞서 필요성을 언급한 트랜잭션·장애 복구 전체가 이번 과제의 필수 구현 범위라는 뜻도 아닙니다.
