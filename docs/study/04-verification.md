# 학습 확인과 구현 후 검증 항목

> 현재는 구현 전입니다. 단위·기능 테스트의 기초는 대화에서 다뤘으며, 아래 상세 사례는 구현 후 검증할 계획입니다. 테스트 실행 결과가 아닙니다.

## 대화에서 확인한 이해

| 항목 | 확인한 내용 |
| --- | --- |
| SELECT 처리 | 조건을 통과한 행에서 필요한 컬럼을 가져온다 |
| 테이블 스캔 | 다음 행을 계속 읽으며, 더 읽을 행이 없으면 끝을 알린다 |
| INSERT 대응 | 명시한 컬럼 목록과 값 목록의 같은 위치를 연결한다 |
| 목록 개수 | 컬럼 수와 값 수가 다르면 오류로 처리한다 |
| 스키마 순서 | 컬럼 생략 예제에서는 정의된 순서로 대응한다고 이해했다 |
| append | 새 행을 뒤에 추가하되 끝을 찾으려고 전 행을 읽을 필요는 없다 |
| 저장 형식 | 저장·읽기 규칙이 다르면 원래 값을 복원하지 못한다 |
| CLI 정책 | 첫 실패 후 중단하되 앞서 성공한 문장은 남긴다 |
| 테스트 | 정상 처리·입력 거부·중단 정책을 기본 검증으로 확인한다 |

이는 대화 중 답변을 확인한 범위이며 독립적인 평가나 구현 검증은 아닙니다. 명시한 컬럼 이름으로 스키마를 찾는 방식과 CSV 해석 후 자료형 적용은 설명을 들었지만 추가 확인은 남아 있습니다. DBMS 배경 노트도 이번에 보충한 내용이므로 이해도 확인 전입니다.

## 현재 범위에서 구현 후 확인할 사례

아래 SQL은 확인하려는 동작의 예시입니다. 최종 지원 문법·자료형·저장 형식과 오류 정책을 정한 뒤 실제 테스트로 옮겨야 합니다.

| ID | 입력 또는 상황 | 확인할 결과 |
| --- | --- | --- |
| P1-01 | SELECT name FROM users WHERE id = 1 | 작업·테이블·컬럼·조건이 구분된다 |
| P1-02 | 조건의 1과 '1' | 숫자와 문자열 리터럴의 구분이 보존된다 |
| P1-03 | 존재하지 않는 테이블 또는 컬럼 | 스키마 검사에서 실패하고 파일을 변경하지 않는다 |
| P1-04 | INSERT의 컬럼 2개, 값 1개 | 개수 불일치로 거부하고 기존 데이터가 유지된다 |
| P1-05 | (age, name)에 (25, '영희') 삽입 | 이름을 기준으로 실제 컬럼에 배치된다 |
| P1-06 | 정수 컬럼에 'abc' 삽입 | 자료형 정책에 따라 거부하고 파일을 변경하지 않는다 |
| P1-07 | 기존 행이 있는 파일에 INSERT | 기존 행을 유지하고 새 행이 추가된다 |
| P1-08 | CSV 후보에서 김,철수 또는 김"철수 저장·읽기 | 쉼표·따옴표를 포함한 원래 값이 복원된다 |
| P1-09 | CSV 텍스트의 age를 복원한 뒤 숫자 조건 검사 | 스키마에 맞게 해석한 값으로 비교한다 |
| P1-10 | 조건 일치 행이 0개·1개·여러 개 | 해당 결과 수대로 반환한다; 중복 행 예제는 중복 허용 스키마를 가정한다 |
| P1-11 | 빈 테이블 또는 마지막 기록까지 읽음 | 정상 종료하며 무한 반복하거나 마지막 행을 누락하지 않는다 |

P1-08은 CSV를 선택할 때의 기준입니다. 다른 형식을 선택하면 그 형식의 특수 문자와 값 복원 사례로 바꿉니다.

가장 직접적인 저장 형식 확인은 **같은 행을 저장하고 다시 읽었을 때 값과 자료형이 원래와 같은지** 보는 것입니다. 아직 이 검사를 실행하지 않았습니다.

## 학습과 정책 결정이 더 필요한 경계 사례

SQL의 따옴표·문법 오류, 중복 컬럼 명시, 컬럼 생략·기본값, CSV의 줄바꿈·NULL·인코딩, 파일 손상·쓰기 실패는 추가 학습과 정책 결정이 필요합니다. 지금 단계에서 기대 동작을 임의로 확정하지 않습니다.

## 단위 테스트와 기능 테스트

단위 테스트는 파서·자료형 검사·저장 변환·트리 탐색처럼 작은 기능을 따로 확인합니다. 기능 테스트는 실제 SQL 파일을 CLI에 전달하거나 API를 호출해 출력·저장 데이터까지 확인합니다.

예를 들어 빈 테이블에 다음 SQL 파일을 실행합니다.

```sql
INSERT INTO users (name, age) VALUES ('영희', 25);
INSERT INTO users (name, age) VALUES ('철수');
INSERT INTO users (name, age) VALUES ('민수', 30);
```

기대 결과는 영희만 저장되고, 두 번째 문장의 개수 오류를 출력한 뒤 중단하여 민수는 저장되지 않는 것입니다. 오류 메시지뿐 아니라 종료 상태와 파일 내용도 확인합니다.

첫 문장 실패, 중간 문장 실패, 모두 성공, 빈 입력, 없는 SQL 파일을 추가로 검사합니다. 프로세스를 종료한 뒤 재실행해서 저장 데이터가 남았는지도 확인합니다. 매 테스트는 임시 파일·디렉터리를 사용해 이전 실행과 분리합니다.

SQL 문자열 속 세미콜론·공백, 닫히지 않은 따옴표, 해석 후 남은 토큰도 검증합니다. 문법이 틀렸는데 정상 접두부만 실행하거나 다음 문장으로 넘어가지 않아야 합니다. 주석·NULL·컬럼 생략 같은 미정 문법은 채택한 정책에 맞춰 기대 결과를 확정합니다.

쓰기 실패는 의도적으로 오류를 주입해 확인합니다. 쓰기 전 검증 실패와 일부 기록 뒤 실패를 구분하고, 선택한 복구·중단 정책이 지켜지는지 검사합니다.

## Phase별 요구사항과 현재 상태

| 단계 | 과제가 요구하는 검증 | 현재 상태 |
| --- | --- | --- |
| Phase 1 | SQL 처리 단위·기능 테스트 | 기초 학습과 사례 정리, 구현·실행 전 |
| Phase 2 | B+ 트리 적용, 100만 건 이상 삽입 후 ID 검색·다른 필드 선형 검색 성능 비교 | 트리 기초 설명과 예습·검증 계획 작성 |
| Phase 3 | API 기능 테스트와 병렬 요청 처리 확인 | 예습·검증 계획 작성, 대화 학습 전 |

실행 가능한 테스트 코드와 성능 수치는 아직 없습니다. 요구사항 출처는 [과제 원문](../assignment.md)입니다.

| P2-U05 | 오름차순·내림차순·고정 시드 임의 삽입 | 모든 키 검색 가능 |

| P2-I03 | 프로세스 재시작 | 인덱스 재구성과 ID 유일성 유지 |
| P2-I04 | 파일 기록 뒤 트리 갱신 실패 | 불일치 감지와 복구·중단 정책 |

작은 노드 용량으로 분할을 자주 발생시키고 단순 정렬 맵을 기준 결과로 비교할 수 있습니다. 기준 맵은 검증용이며 B+ 트리 구현을 대신하지 않습니다.

100만 건 이상 성능 비교는 [실험 계획](phase-2/04-benchmark.md)에 따라 환경·경로·결과 수·시간·메모리를 기록합니다. 현재 성능 우위를 증명한 수치는 없습니다.

## 예습: Phase 3 검증 사례

| ID | 상황 | 확인할 것 |

| P3-F02 | 잘못된 요청·SQL·과도한 크기 | 요청별 오류와 서버 정상 유지 |

| P3-C02 | 쓰기와 ID/스캔 조회 겹침 | 정한 일관성 규칙 준수 |
| P3-C03 | 분할 중 동시 조회·삽입 | 손상·누락·교착 없음 |

스레드를 많이 실행했다는 사실만으로 안전성을 증명하지 않습니다. 장벽 등으로 ID 부여·분할 같은 경쟁 구간을 의도적으로 겹치게 하고, 제한 시간으로 교착을 탐지하며, 최종 데이터와 조회 결과를 검사합니다.

예외 시 락 해제, 같은 풀 안에서 다른 작업을 기다리는 교착, 다른 프로세스의 파일 접근도 선택한 지원 범위에 맞춰 확인합니다.

## 실행 결과를 기록할 때

입력·기대 결과·실제 결과·실행 명령·환경을 남깁니다. 실패 사례와 수정 이유도 보존합니다. 기능 완료, 성능 우위, 동시성 안전을 각각 실제 증거에 맞춰 주장합니다.
