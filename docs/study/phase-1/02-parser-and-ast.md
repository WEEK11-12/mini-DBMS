# SQL 파서와 AST

## 파서의 입력과 결과

파서는 SQL 문자열을 읽고 요청의 구조를 표현합니다.

```sql
SELECT name FROM users WHERE id = 1;
```

| 항목 | 내용 |
| --- | --- |
| 작업 | 조회 |
| 대상 테이블 | users |
| 가져올 컬럼 | name |
| 조건 | id = 1 |

트리 형태로 표현한 예시는 다음과 같습니다. 이를 AST(추상 구문 트리)라고 부릅니다. 아래 모양은 개념 예시이며 과제의 자료구조를 확정한 것이 아닙니다.

```text
SELECT 문
├─ 가져올 컬럼: name
├─ 대상 테이블: users
└─ 조건: =
   ├─ 왼쪽: 컬럼 id
   └─ 오른쪽: 숫자 1
```

## 조건을 나누어야 하는 이유

사용자가 요청한 것은 id 컬럼의 값이 1인 행입니다. id, =, 1의 역할을 구분하지 못하면 id = 1 전체나 id = 같은 문자열을 컬럼 이름으로 취급하는 잘못된 해석이 생길 수 있습니다.

## 숫자와 문자열

```text
id = 1    → 컬럼(id) = 숫자(1)
id = '1'  → 컬럼(id) = 문자열("1")
```

따옴표가 있는 '1'은 문자열 리터럴로 기록합니다. 파서가 이 차이를 보존해야 이후 단계에서 적절하게 처리할 수 있습니다.

## 아직 다루지 않은 범위

INSERT도 작업·테이블·컬럼 목록·값 목록으로 구조화할 수 있다는 점까지 이어서 공부했습니다. 예제는 [INSERT 처리](05-insert.md)에 정리합니다.

토큰화 구현, 상세 문법 규칙, SQL 문자열 이스케이프, 문법 오류 처리 구현은 대화에서 아직 다루지 않았습니다. 아래 예습에서 개념을 보충합니다. 파일 저장 예제에서 다룬 CSV 이스케이프와 SQL 문법의 이스케이프는 구분합니다.

## 예습: 토큰화와 구문 분석을 나눈다

토큰화는 SELECT 같은 키워드, 컬럼 식별자, 숫자·문자열, 쉼표·괄호·연산자를 구분합니다. 공백으로만 나누면 공백이 든 문자열을 보존할 수 없습니다. 문자열을 모두 대문자로 바꾸면 사용자가 넣은 값도 바뀌므로 키워드 비교와 원래 값을 구분합니다.

구문 분석은 토큰 순서가 지원 문법에 맞는지 확인하고 AST를 만듭니다. 예를 들어 INSERT의 괄호·VALUES 위치, SELECT의 FROM 위치, 비교식의 좌우 피연산자를 검사합니다. 해석한 뒤 남은 토큰도 검사해야 잘못된 뒷부분을 무시하지 않습니다.

문법 범위를 먼저 명시해야 합니다. INSERT·SELECT는 필수이고 Phase 2의 ID 조건과 다른 필드 조건이 필요합니다. 지원 비교 연산자, WHERE 생략, 별표, 대소문자·식별자, 문자열 따옴표·주석 규칙은 구현 설계에서 정합니다. JOIN·집계·서브쿼리·임의 SQL 전체를 구현할 필요는 없습니다.

오류는 문장 번호와 토큰 위치를 포함하면 원인을 찾기 쉽습니다. 이 부분은 이번 문서에서 보충한 예습이며 아직 코드를 추적하거나 구현하지 않았습니다.
