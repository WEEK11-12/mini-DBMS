# CLI와 SQL 파일 입력

> CLI 흐름과 오류 시 중단 정책은 함께 논의했습니다. 문장 구분의 상세 구현과 종료 코드는 예습·설계 후보이며 아직 구현하지 않았습니다.

## CLI는 SQL 처리기의 입구다

```text
명령행 인자로 SQL 파일 경로 받기
→ 파일 읽기
→ SQL 문장 구분
→ 순서대로 파싱·검증·실행
→ 결과 또는 오류 출력
```

`mini-db queries.sql`은 명령의 형태를 보여 주는 예시입니다. SQL 파일은 명령을 담고, 테이블 파일은 저장한 데이터를 담습니다. 둘은 다른 파일입니다.

## 세미콜론은 문자열 밖에서 문장을 끝낸다

```sql
INSERT INTO users (name, age) VALUES ('김;철수', 28);
SELECT name FROM users;
```

문자열 안의 세미콜론까지 단순 분할하면 첫 문장이 깨집니다. 문장 구분기는 현재 문자열 안인지, 따옴표가 이스케이프되었는지 구분해야 합니다. SQL 주석을 지원하면 주석 상태도 고려합니다. 지원하지 않는 문법은 명확히 거부하는 편이 안전합니다.

빈 문장, 파일 끝의 세미콜론 생략, 여러 줄 SQL, 따옴표가 닫히지 않은 입력의 정책도 설계 때 정해야 합니다. 개행마다 SQL 한 개라고 가정하지 않습니다.

## 결정한 기본 정책: 첫 실패에서 중단

```text
첫 INSERT 성공 → 저장 유지
두 번째 SQL 실패 → 오류 출력 후 중단
세 번째 SQL → 실행하지 않음
```

처음에는 실패한 문장을 건너뛰고 계속 실행하는 방법을 제안했습니다. 이후 문장 사이의 의존성을 검토하고, 최초 실패 뒤 중단하는 것을 1차 방어로 선택했습니다.

SQL 파일을 읽을 수 없으면 처리할 문장 자체가 없으므로 실행을 시작하지 않습니다. 개별 SQL 오류는 그 문장과 위치를 알리고 중단합니다. 문장 경계를 복구할 수 없는 파싱 오류도 계속 진행하지 않습니다.

정상 결과와 오류를 구분해 출력하고 실패 시 비정상 종료 코드를 반환하면 다른 프로그램에서도 실패를 확인할 수 있습니다. 구체적인 출력 형식과 코드 값은 미정입니다.

## 중단과 롤백은 다르다

중단해도 이전에 성공한 INSERT는 남습니다. 파일 쓰기 중 오류가 났다면 실패한 문장의 일부가 남았을 가능성도 있습니다. 따라서 오류 메시지가 곧 “파일이 전혀 바뀌지 않았다”는 뜻은 아닙니다.

전체 취소가 필요하면 트랜잭션과 복구 장치가 필요합니다. 실패한 문장을 제외한 나머지가 실행 가능한지는 외래 키 같은 관계 검사와도 별개입니다.

실제 제품은 자동 커밋과 명시적 트랜잭션을 구분합니다. PostgreSQL의 트랜잭션 안 오류와 MySQL InnoDB의 일부 문장 오류 처리도 다릅니다. SQL 파일의 나머지를 보낼지는 클라이언트 정책일 수 있습니다. PostgreSQL psql은 오류 후 계속 처리하는 기본값과 ON_ERROR_STOP 설정을 제공합니다.

- [PostgreSQL 트랜잭션](https://www.postgresql.org/docs/18/tutorial-transactions.html)
- [MySQL InnoDB 오류 처리](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)
- [psql 설정](https://www.postgresql.org/docs/18/app-psql.html#APP-PSQL-VARIABLES)

## 예습: 실행 순서와 메모리 사용

파일 전체를 읽는 방식은 단순하지만 큰 입력 파일은 메모리를 많이 사용합니다. 스트리밍 문장 구분은 상태 관리가 더 필요합니다. 100만 INSERT 파일을 사용할지 전용 생성기를 사용할지와 함께 선택합니다.

실행 전에 전체 파일을 파싱하면 뒤의 문법 오류를 미리 찾을 수 있지만, 실행 중 파일 오류까지 막지는 못합니다. 이것만으로 전체 원자성이 생기지는 않습니다.
