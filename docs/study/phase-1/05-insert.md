# INSERT 처리

## 문자열에서 구조로

```sql
INSERT INTO users (name, age) VALUES ('영희', 25);
```

```text
INSERT 문
├─ 대상 테이블: users
├─ 컬럼 목록: [name, age]
└─ 값 목록: [문자열("영희"), 숫자(25)]
```

이 트리는 개념 예시입니다. 실제 AST 자료구조를 결정한 것은 아닙니다.

## 컬럼 목록과 값 목록의 같은 위치를 연결한다

```text
컬럼 목록: [name,   age]
값 목록:   ["영희", 25]
             ↓      ↓
            name   age
```

대응 기준은 각 목록 내부의 위치입니다. 트리 전체에 번호를 붙여 연결하는 방식은 아닙니다. 이때 배열의 위치를 뜻하는 인덱스와 검색용 데이터베이스 인덱스는 다른 의미입니다.

명시한 컬럼 수와 값 수가 다르면 대응시킬 수 없으므로 오류로 처리해야 합니다. 이는 먼저 SQL 문장 내부의 두 목록이 맞는지 검사하는 것이며, 실제 스키마 검사는 별도로 필요합니다.

## 이름으로 실제 컬럼을 찾고, 자료형으로 적합성을 확인한다

스키마가 name: 문자열, age: 정수인 상황에서 아래 요청도 해석할 수 있습니다.

```sql
INSERT INTO users (age, name) VALUES (25, '영희');
```

먼저 요청 내부 순서로 age ↔ 25, name ↔ '영희'를 연결합니다. 이어서 스키마에서 그 이름의 컬럼을 찾아 존재 여부와 자료형을 확인하고, 실제 컬럼에 맞게 값을 배치합니다.

자료형만 보고 값을 어느 컬럼에 넣을지 추측하지 않습니다. name과 email처럼 같은 자료형을 쓰는 컬럼이 여러 개일 수 있기 때문입니다.

## 컬럼 이름을 생략한 경우

```sql
INSERT INTO users VALUES ('영희', 25);
```

지금까지 다룬 단순한 스키마에서는 스키마에 정의된 컬럼 순서로 값을 대응시키는 것으로 이해했습니다. 그 뒤 개수와 자료형을 검사합니다.

기본값, 자동 생성 컬럼, 컬럼 일부 생략, 중복 컬럼 명시 등의 상세 규칙은 아직 다루지 않았습니다. 컬럼 목록 생략을 과제에서 지원할지도 미정입니다.

## 저장까지의 흐름

```text
SQL 파싱
→ 컬럼과 값의 대응 확인
→ 스키마 검증
→ 저장 형식으로 변환
→ 기존 파일 끝에 추가
```

기존 행을 유지하면서 새 행을 추가해야 합니다. 다만 파일 끝을 찾기 위해 모든 행을 읽을 필요는 없습니다. 추가 모드(append)로 파일을 열어 끝에 쓸 수 있습니다. 추가 모드 자체가 스키마 검사나 여러 작업 사이의 안전성까지 해결해 주는 것은 아닙니다.

실제 쓰기 실패 처리와 동시 INSERT는 아직 학습하지 않았습니다.
