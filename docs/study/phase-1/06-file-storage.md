# 파일 저장과 읽기

## 저장할 때와 읽을 때 같은 규칙이 필요하다

파일에는 바이트가 저장됩니다. 저장한 내용을 다시 읽어서 원래 컬럼 값으로 복원하려면 형식 규칙을 정해야 합니다.

```text
원래 행 → 정해진 형식으로 저장 → 같은 형식으로 읽기 → 원래 값 복원
```

과제는 CSV / binary / custom 등을 허용합니다. 지금까지는 CSV 예제로 문제를 살펴봤으며 저장 형식은 확정하지 않았습니다.

## 파일 뒤에 추가하기

한 줄을 한 행으로 생각하는 단순한 예제입니다.

```text
기존 파일:          INSERT 후:
영희,25            영희,25
                   철수,28
```

기존 데이터를 덮어쓰지 않고 새 내용을 뒤에 추가합니다. 파일을 append 모드로 열면 끝을 찾기 위해 처음부터 각 행을 순회할 필요가 없습니다.

append는 데이터 내용을 검사하거나 줄바꿈을 자동으로 넣어 주는 기능은 아닙니다. 행을 구분하는 규칙도 저장 코드가 지켜야 합니다. 운영체제 버퍼·디스크 반영과 동시 쓰기 보장은 아직 다루지 않았습니다.

## 쉼표가 값에 포함된 경우

이름이 김,철수이고 나이가 28이라면 단순히 아래처럼 쓰는 데 문제가 있습니다.

```text
김,철수,28
```

쉼표마다 나누면 세 항목으로 해석되어 name, age 두 컬럼에 맞지 않습니다. CSV에서는 쉼표가 든 값을 큰따옴표로 감쌀 수 있습니다.

```text
"김,철수",28
→ ["김,철수", "28"]
```

읽는 쪽은 큰따옴표 안의 쉼표를 값의 일부로 처리해야 합니다. 단순한 쉼표 분할만으로는 충분하지 않습니다.

## 큰따옴표도 값에 포함된 경우

값 자체가 김"철수라면 CSV에서는 값 안의 큰따옴표를 두 번 써서 표현합니다.

```text
원래 이름: 김"철수
CSV 저장: "김""철수",28
복원한 이름: 김"철수
```

특별한 의미가 있는 문자를 값으로 표현하는 처리를 이스케이프라고 합니다. 작은따옴표로 바꾸는 것은 원래 값을 바꾸는 일입니다. 작은따옴표와 큰따옴표는 크고 작은 단계가 아니라 별개의 문자입니다.

저장 코드와 읽기 코드의 규칙이 다르면 원래 값을 복원하지 못하거나 읽기 오류가 발생합니다.

## SELECT에서 조건을 검사하기 전

```text
파일에서 읽은 기록: "김,철수",28
CSV 규칙 해석:     ["김,철수", "28"]
스키마 적용:       name = 문자열 "김,철수", age = 정수 28
조건 평가:         age = 28인지 검사
```

큰따옴표 짝 확인은 형식 해석의 일부입니다. 최종적으로 컬럼별 값을 복원하고, 스키마에 맞게 해석한 뒤 조건을 검사해야 합니다. CSV 텍스트의 28 자체가 정수형 정보를 갖는 것은 아닙니다.

SQL 파서는 SQL 문장을 구조화하고, CSV 읽기 코드는 저장된 기록을 컬럼 값으로 복원합니다. 두 역할을 구분하는 확인 질문은 아직 답변하지 않았습니다.

## 아직 다루지 않은 범위

값 안의 줄바꿈, 빈 문자열과 NULL, 파일 인코딩, 손상된 기록, 중간 쓰기 실패, 레코드 위치 표현은 아직 다루지 않았습니다. 특히 일반 CSV는 값 안의 줄바꿈을 허용할 수 있으므로 물리적인 한 줄이 항상 한 레코드라는 가정은 추후 확인해야 합니다.

CSV 예제는 기본 형식 규칙을 이해하기 위한 것이며, CSV 파서 직접 구현 여부나 라이브러리 선택도 미정입니다.

## 예습: 저장 형식을 고를 때 남은 질문

CSV는 직접 확인하기 쉽지만 자료형은 스키마로 복원해야 하고, 인용된 개행과 NULL 표현도 정해야 합니다. 바이너리는 길이·자료형을 명시할 수 있지만 정수 바이트 순서, 문자열 길이·인코딩, 형식 버전과 손상 감지를 함께 설계해야 합니다. 어느 쪽이든 표준 라이브러리가 있다면 형식 처리를 재사용할 수 있습니다.

버퍼에 쓴 것, 운영체제로 flush한 것, 저장장치에 내구성 있게 반영한 것은 같은 보장이 아닙니다. 정상 종료 후 재읽기와 프로세스·전원 장애 후 복구를 구분해야 합니다. 완전한 장애 복구는 과제 필수로 가정하지 않고 보장 범위를 문서화합니다.

한 번의 INSERT에서 실패했다고 일부 쓰기가 자동으로 취소되지는 않습니다. 기록 전 검증, 부분 쓰기 감지, 잘린 마지막 레코드의 시작 시 처리, 인덱스와 파일의 복구 정책을 결정해야 합니다. 연결 위치 문제는 [Phase 2 파일·인덱스 연동](../phase-2/03-index-integration.md)에서 이어집니다.
