# 인덱스의 역할과 선택 비용

## 왜 인덱스를 사용하는가

인덱스는 조건에 맞는 행을 찾을 때 검색 대상을 좁히는 데 도움을 줍니다. 인덱스가 없으면 테이블의 행을 차례로 검사하는 전체 스캔을 사용할 수 있습니다.

id에 B+ 트리 인덱스가 있는 경우 id = 1을 찾기 위해 트리를 따라 해당 항목으로 이동할 수 있다는 수준까지 이야기했습니다. 트리 구조와 탐색·삽입·분할 알고리즘은 아직 다루지 않았습니다.

인덱스는 조건에 맞는 행의 위치를 찾는 데 사용할 수 있고, 그 위치의 행에서 name을 읽을 수 있다고 설명했습니다. 인덱스가 언제나 위치만 저장한다는 뜻은 아니며, 이 과제의 인덱스 값 구조는 아직 결정하지 않았습니다.

## 검색 대상을 얼마나 좁히는가

이메일처럼 한 사용자를 특정하기 쉬운 값과 성별처럼 많은 행이 같은 값을 갖는 속성을 비교했습니다. 중요한 기준은 실제 검색 조건에서 후보 행을 얼마나 줄일 수 있느냐입니다. 이메일의 유일성은 실제 제약 조건에 따라 달라집니다.

“한 사용자를 특정할 수 있다”는 생각은 검색 범위를 매우 좁힐 수 있는 예에 해당합니다.

## 모든 컬럼에 인덱스를 만들지 않는 이유

인덱스도 저장 공간과 관리 비용이 필요합니다. 데이터가 변경되면 관련 인덱스도 맞게 갱신해야 합니다.

이전 대화에서 이메일 변경에 따른 인덱스 갱신 비용을 질문한 기록이 있습니다. 그 답변 본문은 확인하지 못했으므로 구체적인 갱신 방식은 아직 정리하지 않습니다.

## 전체 스캔이 더 나을 수 있는 경우

거의 모든 행이 조건에 맞으면 결국 대부분의 행을 읽어야 하므로 검색 대상을 좁히는 이점이 작습니다. 인덱스를 따라 찾은 뒤 각 행에 다시 접근하는 비용까지 있다면 전체 스캔이 더 효율적일 수 있습니다.

따라서 인덱스가 존재한다는 이유만으로 모든 조회가 더 빠르다고 판단할 수는 없습니다. 실제 속도는 아직 측정하지 않았습니다.

## 아직 다루지 않은 범위

B+ 트리의 내부 구조, 자동 ID, 파일 내 레코드 위치 표현, 인덱스 연결·재구성, 성능 측정은 빈 후속 노트에 남깁니다.
