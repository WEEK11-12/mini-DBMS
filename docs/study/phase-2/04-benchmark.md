# 100만 건 생성과 성능 비교

> 전체가 예습·실험 계획입니다. 데이터를 생성하거나 성능을 측정한 결과는 아직 없습니다.

## 과제에서 요구하는 비교

최소 1,000,000개 레코드를 삽입한 뒤 ID 기준 SELECT의 인덱스 탐색과 다른 필드 SELECT의 선형 탐색을 비교합니다. 빠르다는 설명만으로는 인덱스가 실제 사용되었는지 증명할 수 없습니다.

## 먼저 정확성을 확인한다

같은 ID 조건을 강제로 전체 스캔한 결과와 인덱스로 조회한 결과가 일치하는지 확인합니다. 이 확인은 성능 비교를 해석하기 위한 추가 기준입니다.

과제 필수 비교는 ID와 다른 필드의 비교입니다. 여기에 같은 조건의 인덱스 사용·미사용 비교를 보태면 자료형·결과 수 차이의 영향을 줄여 탐색 경로 차이를 보기 쉽습니다.

## 재현 가능한 입력을 만든다

고정 시드로 데이터를 생성하고 스키마, 문자열 길이, 값 분포, 삽입 순서를 기록합니다. 다른 필드에도 고유한 검색 값을 넣으면 한 건을 찾는 조건끼리 비교할 수 있습니다. 중복값이 많다면 일치 건수를 함께 적습니다.

자동 ID를 쓰는 실제 엔진 삽입 경로를 통과시켜 파일과 인덱스를 함께 구성합니다. B+ 트리만 따로 채운 결과를 SQL 연동 완료로 기록하지 않습니다. 생성은 스트리밍 또는 묶음 단위로 해서 100만 객체를 한꺼번에 메모리에 둘 필요를 줄입니다.

SQL 파일 경유와 전용 생성기 중 무엇을 썼는지 공개하고, 최종 조회는 Phase 1 SQL 처리기로 수행합니다.

## 시간을 구간별로 나눈다

| 구간 | 기록할 것 |
| --- | --- |
| 데이터 준비 | 생성 시간, 총 삽입 시간, 실패·성공 건수 |
| 시작 | 파일 열기와 인덱스 재구성 시간 |
| 조회 | 파싱부터 결과 생성까지의 시간 또는 탐색 구간 시간 |
| 메모리 | 인덱스 구성 전후 사용량과 측정 방법 |

벽시계 조정에 영향받지 않는 단조 증가 고해상도 타이머를 사용합니다. 터미널 출력이나 네트워크를 포함했는지 명시합니다. 검색만 비교하려면 대량 출력은 측정 구간에서 분리하되 결과 수를 검증합니다.

## 한 번의 숫자로 결론 내리지 않는다

존재하는 ID, 없는 ID, 앞·중간·뒤에 있는 ID를 여러 번 조회합니다. 측정 순서를 섞고 워밍업 여부를 기록합니다. 평균뿐 아니라 중앙값·최솟값·최댓값 또는 충분한 표본의 상위 지연을 함께 봅니다.

OS 파일 캐시와 메모리 인덱스는 조건을 바꿉니다. “콜드 캐시”를 실제로 통제하지 않았다면 그렇게 이름 붙이지 않습니다. 운영체제·하드웨어·언어 버전·노드 용량·파일 형식·반복 횟수도 기록합니다.

ID가 유일하므로 찾은 뒤 멈춘 스캔과, 다른 필드의 모든 일치 행을 찾는 스캔은 해야 할 일이 다를 수 있습니다. 결과 수와 종료 조건을 함께 비교해야 합니다.

## 보고서에 남길 형태

```text
레코드 수 / 데이터 분포 / 조회 조건 / 예상·실제 결과 수
인덱스 사용 여부 / 측정 범위 / 반복 횟수
선형 탐색 시간 / 인덱스 탐색 시간 / 속도 비율
구성 시간 / 메모리 / 실행 환경 / 한계
```

속도 비율은 같은 단위의 선형 시간 ÷ 인덱스 시간으로 계산합니다. 측정하지 않은 배수나 우위를 미리 적지 않습니다.
