# 자동 ID와 저장 파일·인덱스 연결

> Phase 1 구현 후 ID·파일 위치 연결과 인덱스 등록 실패 정책을 합의했습니다. 아래 현재 결정 이후의 내용에는 비교한 대안과 남은 설계 질문이 포함됩니다. Phase 2 코드는 아직 없습니다.

## 현재 결정과 구현 경계

리프는 ID → 레코드 시작 바이트 위치를 저장합니다. 위치는 SQL 텍스트가 아니라 users.jsonl에 저장된 행의 시작 위치입니다. Phase 1의 append는 이미 ID와 바이트 위치를 반환하지만 B+ 트리에 등록하지는 않습니다.

Phase 2의 INSERT 흐름은 검증 → 파일 기록·flush → 인덱스 등록 → 성공 반환입니다. 파일 저장 후 인덱스 등록에 실패하면 데이터가 이미 저장됐을 수 있음을 알리고 이후 DB 작업을 중단합니다. 파일을 자동 삭제하거나 되돌리지 않고 보존합니다. 재시작 시 파일 전체 검증과 함께 메모리 인덱스를 다시 만듭니다.

자동 ID는 현재 Phase 1에서 정상 저장마다 1씩 증가합니다. 저장된 ID 공백은 허용하고 중복·역순은 거부합니다. ID 공백 자체는 B+ 트리 오류가 아닙니다.

B+ 트리 구조 자체를 별도 파일에 직렬화·복원하는 방법도 이야기했습니다. AST는 SQL의 구조 표현이고 B+ 트리는 검색 인덱스입니다. 트리 파일을 따로 두면 테이블과의 최신성·일관성을 확인해야 하므로 첫 구현은 기존 테이블 검증 순회에서 재구성하는 방향입니다.

## 인덱스가 찾은 값으로 실제 행까지 접근해야 한다

```text
WHERE id = 42
→ B+ 트리에서 42 탐색
→ 42의 레코드 위치 확인
→ 파일의 해당 위치에서 레코드 읽기
→ 나머지 조건 검사·요청 컬럼 반환
```

리프 항목을 ID → 파일 위치로 구성하는 방법이 있습니다. 예를 들어 42 → 바이트 오프셋 1024라면 파일의 1024번째 바이트로 이동해 행을 복원합니다. 구체적인 값은 예시입니다.

인덱스에 행 번호만 저장하고 매번 처음부터 그 행까지 읽으면 검색 뒤에도 선형 읽기가 남습니다. 위치를 찾는 비용과 실제 행 접근 비용을 모두 고려해야 합니다.

## 저장 형식과 위치 표현은 함께 고른다

고정 길이 레코드는 번호로 위치를 계산하기 쉽지만 가변 문자열 처리와 공간 낭비를 고려해야 합니다. 가변 길이 레코드는 시작 위치와 길이 또는 경계 구분 규칙이 필요합니다.

CSV라면 따옴표 속 개행 때문에 물리적인 줄 번호와 레코드 번호가 다를 수 있습니다. UTF-8 문자 수는 바이트 수와도 다릅니다. 텍스트 스트림의 위치값을 언제나 바이트 오프셋으로 취급하지 않습니다. 바이트 단위로 seek할 설계라면 쓰기와 읽기의 위치 규칙을 일치시켜야 합니다.

파일 앞부분을 다시 쓰거나 레코드를 이동하면 기존 오프셋이 무효가 됩니다. 과제의 append 중심 동작은 이를 단순화할 수 있지만 수정·삭제를 추가하면 재검토해야 합니다.

## 자동 ID는 데이터와 함께 남긴다

매 INSERT마다 파일 전체를 읽어 최대 ID를 찾으면 대량 삽입 비용이 커집니다. 시작할 때 저장 데이터를 확인해 다음 ID를 준비하고, 실행 중에는 카운터로 부여하는 방법이 있습니다.

재시작 후에도 ID를 복원하려면 실제 레코드에 부여된 ID가 저장되어 있어야 합니다. append만 하는 단순 모델에서는 시작 시 최대 ID + 1을 후보로 삼을 수 있습니다. 삭제 뒤 ID 재사용 금지까지 요구하면 별도 영속 시퀀스 정책이 필요합니다.

실패한 INSERT가 소비한 ID를 재사용할지와 ID 공백 허용 여부도 정해야 합니다. 중복 방지가 중요하며 연속 번호 자체가 필수 요구는 아닙니다.

## INSERT가 파일과 인덱스를 함께 바꾼다

```text
입력 검증
→ ID 부여
→ 저장 위치 확보·레코드 기록
→ ID와 위치를 B+ 트리에 등록
→ 성공 결과 반환
```

이 흐름만 적었다고 원자성이 보장되지는 않습니다. 파일 기록 후 인덱스 등록에 실패하면 파일과 인덱스가 불일치할 수 있습니다. 이때 성공을 응답하거나 “아무것도 저장되지 않았다”고 응답하면 안 됩니다.

복구 방향의 예는 쓰기 전 파일 크기를 기억하고 안전한 조건에서 되돌리거나, 엔진을 오류 상태로 전환해 새 요청을 막고 파일에서 인덱스를 재구성하는 것입니다. 메모리 트리 부분 변경까지 포함한 복구·검증이 필요합니다. 파일 크기 되돌리기는 단독 쓰기 보장 없이 다른 요청의 데이터를 지울 수 있습니다.

현재는 앞서 적은 오류 보고·중단·재시작 재구성을 선택했습니다. 파일 크기를 되돌리는 방식은 비교 대안이며 채택하지 않았습니다. 로그나 저널을 사용하는 실제 DBMS의 복구는 추가 학습 범위입니다. [SQLite Atomic Commit](https://www.sqlite.org/atomiccommit.html)

## 메모리 인덱스는 재시작하면 사라진다

파일을 기준 데이터로 삼고, 시작 시 레코드를 순회해 인덱스를 재구성할 수 있습니다. 손상된 레코드를 조용히 건너뛰면 ID와 검색 결과가 달라질 수 있으므로 감지·중단 정책이 필요합니다.

재구성 시간과 메모리 사용량은 별도로 측정합니다. 재구성이 끝나기 전 조회 요청을 받지 않도록 초기화 순서도 정합니다.

## Phase 1 처리기를 그대로 연결한다

파서와 스키마 검사는 재사용하고, 실행 단계에서 지원하는 ID 동등 조건이면 인덱스 접근을 고르는 방식이 가능합니다. 다른 필드 조건은 기존 스캔으로 처리합니다.

Phase 1은 문자열 '42'를 정수 ID로 자동 변환하지 않고, 복합 조건도 지원하지 않습니다. 이 규칙을 이어가며 인덱스 사용 여부를 어떻게 관찰할지는 아직 결정해야 합니다. 지원하지 않는 조건까지 잘못 인덱스로 처리하지 않아야 합니다.
