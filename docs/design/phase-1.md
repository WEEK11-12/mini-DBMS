## 1. 목적과 합의한 범위

SQL 파일을 CLI로 받아 INSERT / SELECT를 실행하고, 재실행 후에도 파일에서 데이터를 읽을 수 있는 처리기를 만든다. Phase 2의 B+ 트리와 Phase 3의 API가 같은 처리기를 재사용한다.

다음은 대화에서 합의한 내용이다.

| 항목 | 결정과 이유 |
| --- | --- |
| 언어 | Python. 문자열·가변 자료구조의 메모리 관리 부담을 줄이고 처리 흐름과 정확성에 집중 |
| SQL 범위 | 컬럼 목록을 명시한 단일 행 INSERT, SELECT의 별표·컬럼 선택, 선택적인 동등 조건 하나 |
| 스키마 | 코드에 users(id: 자동 정수, name: 필수 문자열, age: 필수 정수) 정의 |
| 저장 | 테이블별 JSON Lines. 사람이 저장된 행을 직접 확인하기 쉬움 |
| 자동 ID | INSERT 구현과 함께 Phase 1에 선반영. Phase 2에서 같은 ID를 인덱스에 연결 |
| SQL 오류 | 첫 실패 이후 문장 실행 중단. 앞서 성공한 문장은 유지 |
| INSERT 성공 | 행 전체와 줄바꿈을 기록하고 flush까지 성공한 뒤 반환 |
| 재시작 | 전체 파일을 한 행씩 복원·검증하고 최대 ID + 1 준비. 빈 테이블은 1 |
| 손상 발견 | 파일 위치와 원인을 알리고 사용 중단. 자동 삭제·건너뛰기 없음 |
| 초기화 | 별도 명령으로 디렉터리·빈 테이블 파일 준비. 기존 파일을 덮어쓰지 않음 |
| 일반 실행 | 테이블 파일이 없으면 오류 |

CREATE TABLE, UPDATE·DELETE, JOIN·집계·정렬, 복합 조건, 트랜잭션 전체 취소, 장애 자동 복구는 첫 구현 범위에 포함하지 않는다. B+ 트리·API 서버는 후속 Phase에서 추가한다.

## 2. 비교한 접근과 선택

| 선택 | 고려한 대안 | 선택 이유·비용 |
| --- | --- | --- |
| Python | C | C로도 전체 기능을 구현할 수 있다. 이번에는 버퍼·할당·해제보다 엔진 흐름을 우선. 메모리 배치의 정밀 제어는 제한됨 |
| JSON Lines | CSV | 컬럼 이름과 값이 보이며 표준 JSON 처리 사용 가능. 같은 키가 반복되어 파일이 커질 수 있음 |
| 시작 시 파일 전체 검사 | 파일 끝의 ID만 읽기, 별도 ID 파일 | 시작 비용은 O(N)이지만 모든 행을 검증하고 Phase 2 재구성 순회와 합칠 수 있음. 별도 상태 파일의 불일치를 피함 |
| 첫 오류 후 중단 | 실패 문장만 건너뛰고 계속 | 앞선 실패에 의존하는 후속 작업 진행을 줄임. 이미 성공한 문장은 취소하지 않음 |

## 3. 초안을 완결하기 위해 제안한 기본값

아래 항목은 합의한 원칙을 구체화한 기본값이다. 사용자가 이 내용을 검토한 뒤 Phase 1 구현을 지시하여 첫 구현 기준으로 적용했다. 별도의 범위 변경 없이 구현 중 필요한 세부 사항을 결정한다.

- Python 표준 라이브러리만 사용한다. JSON은 json, CLI는 argparse, AST·결과는 dataclasses, 테스트는 unittest를 사용한다.
- 테이블 파일은 지정한 데이터 디렉터리의 users.jsonl이다. SQL의 테이블 이름은 고정 스키마에서 찾아 파일에 매핑한다.
- 키워드는 대소문자를 구분하지 않는다. 식별자는 ASCII 영문·숫자·밑줄 형식으로 제한하고 소문자로 정규화한다. 따옴표 식별자는 지원하지 않는다.
- 값은 부호 없는 또는 음수의 10진 정수와 작은따옴표 문자열이다. 문자열 안 작은따옴표는 두 번 쓰고, 백슬래시를 SQL 이스케이프로 해석하지 않는다.
- 정수는 부호 있는 64비트 범위다. ID는 1부터 시작하는 양의 정수이고 범위를 넘으면 삽입을 거부한다. Python bool을 정수형 레코드 값으로 허용하지 않는다.
- INSERT는 name과 age를 각각 한 번씩 모두 지정한다. 순서는 바꿀 수 있다. id 직접 지정, 기본값·NULL·자동 형 변환은 허용하지 않는다.
- SELECT의 WHERE는 컬럼 = 리터럴 하나다. 중복 출력 컬럼은 거부한다. name 빈 문자열과 age 음수는 자료형상 허용하며 추가 업무 규칙은 넣지 않는다.
- SQL 문장은 문자열 밖 세미콜론으로 끝나야 한다. 빈 문장은 무시하고 공백·여러 줄 입력을 허용한다. SQL 주석과 여러 행 VALUES는 지원하지 않는다.
- JSON Lines는 UTF-8, BOM 없음, 한 행당 JSON 객체 하나와 LF 한 개다. 키 순서는 id, name, age로 쓰되 읽을 때는 키 집합과 자료형으로 검증한다.
- 저장 파일의 빈 줄·중복 JSON 키·여분 컬럼·빠진 컬럼·줄바꿈 없는 마지막 기록은 손상으로 거부한다. JSON 문법이 맞더라도 스키마와 다르면 손상이다.
- 저장 ID는 파일 순서대로 엄격히 증가해야 한다. 번호 공백은 허용한다. 이 append 전용 규칙이면 전체 ID 집합을 메모리에 보관하지 않고 중복도 탐지할 수 있다.
- 한 프로세스만 데이터 디렉터리를 사용한다. 동시 프로세스 접근과 요청 병렬화는 Phase 1의 지원 범위가 아니다.

## 4. SQL 문법과 기대 동작

```sql
INSERT INTO users (name, age) VALUES ('영희', 25);
INSERT INTO users (age, name) VALUES (28, 'O''Brien');
SELECT * FROM users;
SELECT name, age FROM users;
SELECT name FROM users WHERE age = 25;
SELECT name FROM users WHERE id = 1;
```

컬럼 목록과 값 목록을 위치로 대응시킨 뒤 스키마의 컬럼 이름에 연결한다. WHERE의 컬럼과 값도 정확한 자료형으로 비교한다. Phase 1의 ID 조건은 다른 조건과 마찬가지로 파일을 순회한다.

AST 예시는 다음과 같다. 트리를 Python 객체로 표현하므로 별도의 범용 트리 라이브러리는 필요하지 않다.

```text
Insert(table='users', columns=('name','age'), values=('영희',25))
Select(table='users', columns=('name',), condition=Equal('age',25))
```

별표는 AST에서 명시적으로 표시하고, 실행기에서 스키마 순서 id·name·age로 확장한다. WHERE 생략은 조건 없음으로 표현한다.

## 5. 모듈과 입출력

처음부터 여러 추상 계층을 추가하지 않고 아래 책임으로 나눈다. 파일 이름과 인터페이스는 제안이다.

| 모듈 | 주요 입력 → 출력 | 책임 |
| --- | --- | --- |
| cli.py | 명령행 인자 → 종료 코드 | 초기화·실행 명령, SQL 파일 읽기, 결과·오류 출력 |
| parser.py | SQL 텍스트 → 문장 AST | 문자열 상태를 고려한 문장 구분, 토큰화·문법 검사 |
| schema.py | 테이블·컬럼·값 → 검증 결과 | 고정 스키마, 입력·저장 행 검증 규칙 공유 |
| engine.py | AST → InsertResult 또는 SelectResult | 실행 전 스키마 검사, 조건 평가, 컬럼 선택 |
| storage.py | 검증된 값 → 삽입 결과, 읽기 요청 → 행 반복자 | 초기화, 파일 검사·복원, ID·바이트 위치, JSON Lines I/O |
| errors.py | 오류 정보 → 분류된 예외 | 문법·스키마·입력 파일・손상·저장 실패를 구분 |

설정 레지스트리·플러그인·범용 DB 어댑터는 만들지 않는다. 초기 패키지 이름은 mini_dbms로 제안한다.

파서는 테이블이 실제로 존재하는지 알 필요가 없다. 실행기가 AST를 받은 직후 스키마를 검증하고, 통과해야 저장소를 호출한다. 저장소가 외부 입력을 받아 검증을 생략하지 않도록 공유 검증 함수를 사용한다.

### INSERT

```text
CLI → 파서 → AST
→ 실행기의 스키마 검증
→ 저장소: next_id를 붙여 행 구성
→ JSON + LF를 UTF-8 바이트로 직렬화
→ 파일 끝 위치 확인 → 모든 바이트 쓰기 → flush
→ next_id 증가 → InsertResult(id, affected_rows=1)
→ CLI 출력
```

쓰기 길이를 확인하고 남은 바이트가 있다면 처리한다. 쓰기·flush 오류가 나면 저장소를 실패 상태로 두고 닫으며 추가 작업을 막는다. next_id 증가 전이라도 일부 바이트는 남았을 수 있다. 원본을 자동 truncate하거나 삭제하지 않는다.

### SELECT

```text
AST → 스키마 검증 → 저장소의 행 반복자
→ 행마다 조건 평가 → 출력 컬럼 순서로 값 선택
→ SelectResult(columns, rows) → CLI가 차례로 소비
```

SelectResult의 rows는 제너레이터로 전달한다. 스키마 검증은 결과 반환 전에 실행하고, 파일 오류는 반복자를 소비하는 중에도 발생할 수 있다. CLI는 호출과 반복 소비 양쪽의 예외를 처리한다.

## 6. 파일 수명과 재시작

초기화는 디렉터리가 이미 있어도 재사용할 수 있지만 테이블 파일은 배타적 생성으로 준비한다. 파일이 존재하면 비어 있어도 초기화를 거부한다. 확인 후 덮어쓰는 방식은 사용하지 않는다.

일반 실행은 테이블 파일을 생성하지 않는 읽기·쓰기 바이너리 모드로 연다. 전체를 순회하며 줄 위치·바이트 오프셋, UTF-8·JSON·스키마·ID를 검사한다. 검사가 모두 끝나야 SQL 실행을 시작한다.

행 전체를 메모리에 남기지 않고 최대 ID와 직전 ID를 갱신한다. 빈 파일의 next_id는 1이다. 손상 시 파일·줄 번호·바이트 위치와 원인을 알리고 파일을 수정하지 않는다.

JSON 직렬화가 문자열 속 개행을 이스케이프하므로 실제 LF로 레코드를 나눌 수 있다. 문자 수로 오프셋을 계산하지 않고 바이너리 파일 위치를 사용한다. 사용 중인 핸들과 제너레이터는 정상·실패 경로 모두 닫는다.

## 7. CLI 계약과 부분 결과

명령 형태 제안:

```text
python -m mini_dbms init --data-dir data
python -m mini_dbms run queries.sql --data-dir data
```

CLI는 문장 하나씩 구분·파싱·실행한 뒤 다음으로 진행한다. 뒤 문장이 잘못되었다는 이유로 앞선 성공을 취소하지 않는다. UTF-8 읽기나 문장 구분의 실패도 첫 오류 중단 원칙에 포함한다.

출력 기본값은 INSERT 성공 시 ID·영향받은 행 수, SELECT는 컬럼 헤더·행별 JSON 배열·완료 시 행 수를 표시하는 것으로 제안한다. 줄바꿈이 든 값도 출력 경계를 깨지 않도록 이스케이프한다. 결과는 stdout, 오류는 stderr, 성공 종료는 0, 실행 실패는 1, 명령 사용 오류는 2로 구분한다.

SELECT 중간 실패 전에 일부 행이 출력될 수 있다. 이때 완료 표시 없이 오류와 실패 종료 코드로 알린다. 전체 결과를 원자적으로 출력한다고 보장하지 않는다. SQL 파일 경로는 입력용으로만 사용하며 테이블 경로를 SQL 값에서 만들지 않는다.

## 8. 오류 분류와 보장 범위

| 분류 | 예 | 처리 |
| --- | --- | --- |
| 입력 파일 오류 | 없는 SQL 파일·읽기 실패 | SQL 실행 중단, 오류 위치 보고 |
| 문법 오류 | 닫히지 않은 문자열·지원하지 않는 구문 | 해당 문장 저장 전 거부, 뒤 문장 중단 |
| 스키마 오류 | 없는 컬럼·개수·자료형 불일치 | 해당 문장 저장 전 거부, 뒤 문장 중단 |
| 테이블 손상 | JSON 깨짐·자료형·ID 위반 | 시작 또는 읽기 단계에서 저장소 사용 중단 |
| 저장 I/O 오류 | 일부 쓰기·flush 실패 | 상태 불확실성을 보고하고 저장소 사용 중단 |

정상 INSERT 성공은 flush 완료 기준이다. fsync, 전원 장애 내구성, 프로세스 강제 종료 시 복구, 여러 SQL의 트랜잭션은 보장하지 않는다. flush가 데이터 내용의 정확성까지 증명하지 않으므로 읽기 복원·조회 테스트를 별도로 수행한다.

## 9. 검증 기준

| 영역 | 최소 통과 사례 |
| --- | --- |
| 파서 | 지원 SQL, 컬럼 순서, 문자열 속 쉼표·세미콜론·작은따옴표, 잘못된 나머지 토큰 |
| 스키마 | 필수 컬럼·중복·정수 범위·정확한 자료형·id 직접 지정 거부 |
| 초기화 | 새 파일 생성, 기존 파일 내용과 바이트 보존, 일반 실행의 누락 파일 오류 |
| 저장 | 한글·특수문자·개행의 JSON 복원, 두 행 append, 실제 바이트 오프셋 |
| 시작 검사 | 빈 파일·유효 파일·중복/역순 ID·잘린 JSON·잘못된 키·불완전 마지막 줄 |
| SELECT | 전체·컬럼 선택·조건 일치 0/1/여러 행, 잘못된 조건의 실행 전 거부 |
| CLI | 성공 INSERT → 오류 → 후속 INSERT 미실행, 정상·오류 종료 코드 |
| 재시작 | 파일 유지, 다음 ID 복원, 재실행 SELECT 결과 일치 |
| 실패 주입 | 일부 쓰기·flush 실패 후 성공 미응답, 후속 작업 차단, 원본 자동 삭제 없음 |
| 자원 정리 | 조회 중 실패·반복 중단·CLI 종료에서 파일 핸들 회수 |

테스트는 임시 디렉터리에서 실행한다. 별도 프로세스로 초기화·실행·재실행하는 기능 테스트를 포함한다. 자세한 학습용 사례는 [검증 노트](../study/04-verification.md)를 연결하고, 확정 설계와 충돌하면 이 문서를 기준으로 테스트를 갱신한다.

## 10. 후속 Phase와 설계 검토

Phase 2는 같은 시작 순회에서 ID → 바이트 위치를 B+ 트리에 등록하고, ID 동등 조건만 인덱스 접근으로 바꾼다. 현재 단계에서 사용하지 않는 인덱스 추상화나 콜백을 미리 만들지 않는다.

Phase 3는 CLI와 분리된 실행 결과를 API 응답으로 바꾸고 동시성을 추가한다. Phase 1 저장소는 단일 실행 전제이며, 공유 핸들·ID·트리 변경을 보호하는 정책은 Phase 3에서 재설계·검증한다.

Phase 1의 코드와 테스트를 구현했다. 검증 결과와 한계는 검증 노트에 기록하며, Phase 2·3과 벤치마크는 아직 구현·실행하지 않았다.
